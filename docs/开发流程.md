# 开发与发版流程

按这个顺序操作。走错的代价是：没验证的改动进了 `develop`，或者一次推送就打出三个平台的安装包。

## 分支

| 分支 | 作用 |
| --- | --- |
| `develop` | 集成。功能分支从这里切出，验证通过后也回到这里 |
| `test` | 验证沙箱。用完即弃，不往外合并 |
| `master` | 发布。只在发版时接收 `develop`，推送本身不编译客户端 |
| `feature/…` | 功能开发。一个功能一条分支 |

CI：

- 推送 `develop` / `test` / `master`：只跑测试（`.github/workflows/test.yml`）
- 推送打在 `master` 上的 `vX.Y.Z` 或 `vX.Y.Z-rc.1` tag：再跑测试、编译 Windows / Linux / macOS 客户端、创建 GitHub Release（`.github/workflows/release.yml`）
- 带 `-` 的 tag（如 `v1.2.0-rc.1`）标成预发布，不设为 Latest

## 1. 从 develop 切功能分支

```bash
git checkout develop
git pull origin develop
git checkout -b feature/你的功能
```

在这条分支上开发和提交。不要在 `develop`、`test`、`master` 上直接改代码。

## 2. 合进 test 做验证

`test` 每次验证前先重置到当时的 `develop`，再只合入要验的功能分支。这样不会把上一次没通过的改动混进来。

```bash
git checkout test
git fetch origin
git reset --hard origin/develop
git merge feature/你的功能
git push --force-with-lease origin test
```

`--force-with-lease` 只允许用在 `test`。`develop` 和 `master` 禁止强推。

在 `test` 上发现的问题，改回 `feature/你的功能` 再提交，然后重新执行上面的重置和合并。不要在 `test` 上直接改完就算数，那些提交不会跟着进入 `develop`。

## 3. 验证通过后，把功能分支合进 develop

合进去的是功能分支，不是 `test`。

```bash
git checkout develop
git pull origin develop
git merge feature/你的功能
git push origin develop
```

`test` 上如果叠了别的还在验证的功能，合进 `develop` 会把它们一起带上。

## 4. 发版

要发的提交必须已经在 `develop` 上。先推 `master`，再在这个新提交上打 tag。顺序反了的话，发版检查会认为 tag 还不在 `master` 上，直接失败。

```bash
git checkout master
git pull origin master
git merge develop
git push origin master
git tag v1.2.0
git push origin v1.2.0
```

tag 格式只接受 `vX.Y.Z` 或 `vX.Y.Z-rc.1` 这种预发布号。不要在功能分支上打这个 tag。

推送 tag 之后看 Actions 里的 Release 工作流。三个平台的 zip 和校验和会出现在该 tag 的 GitHub Release 里。

## 不要做

- 不要把 `test` 合并进 `develop` 或 `master`
- 不要对 `develop`、`master` 使用 `push --force`
- 不要在功能分支上打 `v*` tag
- 不要先推 tag、后推 `master`
- 不要期待每次推 `master` 都会编译客户端；编译只由 tag 触发
